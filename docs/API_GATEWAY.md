# Архитектура API Gateway и правила интеграции микросервисов

Этот документ определяет единые стандарты, правила маршрутизации, принципы безопасности и сквозной трассировки в экосистеме микросервисов Edusfera через единый API-шлюз (API Gateway).

---

## 1. Архитектура и сетевая топология

Вся экосистема Edusfera взаимодействует через единую точку входа (API Gateway) на базе **Nginx**. Это решает три ключевые задачи:
1. **Безопасность:** Микросервисы работают во внутренней сети Docker (`edusfera`) и не выставляют свои порты во внешний мир.
2. **Единый домен:** Исключаются проблемы с CORS на стороне клиента, так как фронтенд делает запросы на единый хост (`edusfera.by`).
3. **Сквозная трассировка:** Шлюз генерирует или пробрасывает заголовок `X-Request-Id` для трассировки логов между всеми компонентами.

### Схема прохождения запросов:

```
                  ┌──────────────────────┐
                  │ Клиент (Браузер)     │
                  └──────────┬───────────┘
                             │ (порты 80/443)
                             ▼
                  ┌──────────────────────┐
                  │  Nginx API Gateway   │
                  └─┬────────┬─────────┬─┘
                    │        │         │
      ┌─────────────┘        │         └──────────────┐
      │ (Laravel FPM)        │ (REST /ws)             │ (REST /api)
      ▼                      ▼                        ▼
┌───────────┐          ┌───────────┐            ┌───────────┐
│  Laravel  │          │   Media   │            │  Ledger   │
│ (монолит) │          │ (стриминг)│            │ (финансы) │
└───────────┘          └───────────┘            └───────────┘
```

## 2. Единая карта маршрутизации (Routing Rules)

Шлюз маршрутизирует запросы на основе префиксов путей. Все микросервисы используют версионирование `v1`.

| Внешний путь на Gateway | Внутренний целевой адрес | Описание | Примечание |
| :--- | :--- | :--- | :--- |
| `/api/v1/ledger/*` | `http://ledger:8080/*` | Финансовый микросервис | Префикс `/api/v1/ledger` отсекается шлюзом |
| `/api/v1/media/*` | `http://media:8088/*` | REST API медиа-сервера | Префикс `/api/v1/media` отсекается шлюзом |
| `/ws/*` | `http://media:8088/ws/*` | WebSocket-сигналинг звонков | Поддержка протоколов Upgrade / Connection |
| `/api/v1/*` | `http://app:9000/*` | Публичный REST API ядра | Обрабатывается в Laravel-монолите |
| `/*` (все прочие) | `http://app:9000/*` | Filament-панель, Web-страницы | Laravel-монолит |

## 3. Единая дизайн-система API и контракты

Все новые эндпоинты платформы должны соответствовать стандартам проектирования REST API Edusfera:

1. **Формат ответа:** Все ответы должны возвращаться строго в формате JSON. Запрещена прямая сериализация Eloquent-моделей. Ответы должны оборачиваться в DTO-ресурсы ([Http/Api/V1/Resources/](file:///Users/sergei/Desktop/edusfera.by/app/Http/Api/V1/Resources/)).
2. **Формат ошибок:** Ошибки возвращаются в стандартизированном JSON-конверте:
   ```json
   {
     "error": {
       "code": "insufficient_scope",
       "message": "The token does not have the required scope to access this resource.",
       "request_id": "01J5T3ABCDEF0000000000000000"
     }
   }
   ```
3. **Версионирование в OpenAPI:** Все новые эндпоинты должны быть внесены в спецификацию [openapi.yaml](file:///Users/sergei/Desktop/edusfera.by/docs/api/openapi.yaml). Локальные изменения проверяются на совместимость при CI-сборках.

## 4. Сквозная трассировка (`X-Request-Id`)

Для отладки распределенных запросов используется заголовок `X-Request-Id`:
1. **Генерация:** Nginx принимает внешний заголовок `X-Request-Id` (UUID v4 или v7). Если заголовок отсутствует, middleware `AssignRequestId` генерирует его на бэкенде ядра (UUID v7).
2. **Проброс (Propagation):**
   - Все исходящие S2S HTTP-запросы из ядра к микросервисам обязаны прикреплять заголовок `X-Request-Id`.
   - При публикации интеграционных событий через Outbox, идентификатор запроса сохраняется в поле `trace_id` конверта события.
3. **Логирование:** Все микросервисы должны писать `request_id` во все логи в структурированном виде (JSON-логи).

## 5. Модель авторизации и безопасности

Безопасность шлюза делится на три уровня в зависимости от субъекта запроса:

### А. Конечный пользователь → API Gateway
* Авторизация через **Laravel Sanctum Bearer Token** (Personal Access Token).
* Токен выдается после веб-аутентификации или через ручку авторизации.
* Используется для защиты пользовательских эндпоинтов (например, `GET /api/v1/lessons/{id}/classroom-token`).

### Б. Сервис → Сервис (S2S)
* Авторизация через **OAuth2 Client Credentials Grant** (поддерживается Laravel Passport).
* Каждый микросервис регистрируется как клиент с `client_id` и `client_secret`.
* Токен выпускается асимметричной подписью **RS256**.
* Микросервисы валидируют токен самостоятельно без обращения к ядру, запрашивая и кэшируя публичные ключи из публичной JWKS-ручки шлюза:
  👉 **`GET /api/v1/.well-known/jwks.json`**
* Права доступа ограничиваются областями видимости (**Scopes**), прописанными в [config/oauth.php](file:///Users/sergei/Desktop/edusfera.by/config/oauth.php). Например, микросервис доски должен иметь scope `homework:write` для отправки созданного ИИ домашнего задания.

### В. Вебхук от микросервиса → API Gateway (Ядро)
* Защита с помощью **HMAC-SHA256** подписи.
* Микросервис подписывает тело запроса общим секретным ключом клиента и присылает подпись в заголовке `X-Signature`.
* Ядро верифицирует подпись, а также предотвращает replay-атаки с помощью проверки временного сдвига (`X-Timestamp`) и уникального одноразового токена (`X-Nonce` с кэшированием в Redis).

## 6. Идемпотентность запросов

Для всех mutating-эндпоинтов (POST, PUT, PATCH, DELETE), где дублирование выполнения запроса критично (особенно в биллинге Ledger и при бронировании), шлюз поддерживает заголовок `Idempotency-Key` (UUID).

1. При получении запроса с `Idempotency-Key`, middleware проверяет наличие ключа в Redis (`idem:v1:{client_id}:{key}`).
2. Если запрос выполняется прямо сейчас (состояние `in-flight`), возвращается ошибка `409 Conflict`.
3. Если запрос уже был успешно обработан ранее, возвращается кэшированный HTTP-ответ (статус, тело, заголовки).
4. Если запроса нет в кэше, он обрабатывается, а результат кэшируется на 24 часа.

## 7. Инструкция: Как подключить новый микросервис к шлюзу

Для добавления нового микросервиса (например, `ai-assistant`) выполните следующие шаги:

### Шаг 1: Описать маршруты в конфигурации Gateway
1. Откройте локальный файл конфигурации шлюза [nginx-local.conf](file:///Users/sergei/Desktop/edusfera.by/nginx/nginx-local.conf) и пропишите правила проксирования. Пример:
   ```nginx
   location /api/v1/ai/ {
       rewrite ^/api/v1/ai/(.*)$ /$1 break;
       proxy_pass http://ai-service:8000;
       proxy_set_header Host $host;
       proxy_set_header X-Real-IP $remote_addr;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       proxy_set_header X-Request-Id $request_id;
   }
   ```
2. Пропишите аналогичные настройки в продакшн-конфигурациях [nginx.conf](file:///Users/sergei/Desktop/edusfera.by/nginx/nginx.conf) и [nginx-bare-metal.conf](file:///Users/sergei/Desktop/edusfera.by/nginx/nginx-bare-metal.conf) (заменив имя контейнера на `127.0.0.1:порт` для bare-metal).

### Шаг 2: Обновить Docker Compose
Добавьте ваш микросервис в [docker-compose.yml](file:///Users/sergei/Desktop/edusfera.by/docker-compose.yml):
```yaml
  ai-service:
    build:
      context: ./edusfera-ai
      dockerfile: Dockerfile
    environment:
      PORT: '8000'
      JWT_SECRET: '${CLASSROOM_JWT_SECRET}'
    networks:
      - edusfera
```
Убедитесь, что ваш сервис подключен к общей сети `networks: - edusfera`.

### Шаг 3: Зарегистрировать OAuth2 Scopes (при необходимости)
Если микросервис должен обращаться к ядру (например, обновлять балансы или выставлять оценки):
1. Зарегистрируйте требуемые scopes в [config/oauth.php](file:///Users/sergei/Desktop/edusfera.by/config/oauth.php).
2. Выпустите client_credentials токен с помощью Passport.

### Шаг 4: Документировать контракты
1. Добавьте описание публичных эндпоинтов вашего сервиса в [openapi.yaml](file:///Users/sergei/Desktop/edusfera.by/docs/api/openapi.yaml).
2. Если сервис публикует или слушает интеграционные события, добавьте JSON Schema схемы событий в папку `docs/events/{event-name}.v{version}.json`.
